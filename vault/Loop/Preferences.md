# Preferences

_Durable conventions/decisions the loop applies every iteration. Maintained by `loop-learn`._

## Stack & platform
- **Platform: Web app** (decided in ISSUE-202606131230). **Language: TypeScript.**
- The privacy/domain **core is a pure, dependency-free module** (`src/core/`) so it runs in browser, Node, and tests unchanged. Tests use the built-in **`node:test`** runner (`npm test`) — no external test deps required. _Why:_ keeps the privacy spine verifiable offline with zero install; honors the "no LLM/network at runtime" PRD rule.
- Web UI (later) will use Vite + an open-source JS map library (Leaflet or MapLibre) — no API-key-gated services, so the demo runs offline.

## Working style
- **Code-first**: prioritize shipping runnable, tested code over additional planning/docs (user feedback, [Review 1](../Reviews/processed/Review%201.md)). _How to apply:_ once a task is plannable, move to Implementation quickly; don't accumulate planning artifacts.
- **Parallelize with subagents**: dispatch independent work (planning, review, and implementation) as multiple subagents to accelerate (user feedback, [Review 2](../Reviews/processed/Review%202.md)). _How to apply:_ keep parallel work **verifiable offline** (pure modules + `node:test`); the orchestrator re-runs the **full** suite to verify integration rather than trusting subagent self-reports.
- **Worktree isolation per implementation subagent**: when an implementation subagent works on a task in parallel with others, run it in its own **git worktree** (`Agent` tool `isolation: "worktree"`) to avoid conflicts (user feedback, [Review 3](../Reviews/processed/Review%203.md)). _Why:_ disjoint file ownership alone is fragile — worktrees guarantee no collision on shared files (package.json, lockfiles, config) and let each task's changes be reviewed/merged independently. _How to apply:_ read/review/planning subagents (no writes) don't need a worktree; any subagent that **writes product code** in parallel does. The orchestrator integrates + runs the full suite after merge. See [loop-implement](../../.claude/skills/loop-implement/SKILL.md).
- **Subagent commit/branch ownership**: tell each implementation subagent explicitly whether to commit. Default: a **single, sequential** implementation subagent should leave changes in the working tree (no new branch, no commit) and let the **orchestrator commit on `main`**; only **parallel** code subagents commit, and they do so inside their own worktree branch for the orchestrator to merge. _Why:_ in loop #6 a lone subagent auto-created `feat/...` and committed there, forcing a fast-forward reconciliation back to main.

## Native / standalone shell strategy
- **Wrap the existing web app in a thin native shell; never maintain a parallel native rewrite of the privacy core.** The user pivoted the standalone sender from a Swift/JSC menu-bar app to **Tauri** (ISSUE-...1314, "Let's move to Tauri then."). _Why:_ Tauri (and any webview shell) runs the *unchanged* web privacy core in its webview, so there is one privacy implementation and the map/scrubber/demo/strip are reused verbatim — honoring "reuse, don't rewrite" + the highest-priority privacy guarantee. A second native privacy implementation (porting to Swift) was rejected as too risky. _How to apply:_ for the native send path, the shell owns only tray + global hotkey + window; the send must route through the same in-webview `transformSignal`/`SignalStore` path as the in-page hotkey (e.g. a native event the frontend listens for), so the native path is byte-for-byte the web path.
- **Pick a build toolchain that the machine can actually build.** Swift was blocked by a machine-level SDK/compiler skew (ISSUE-...1314) that the loop can't fix; Tauri builds via Rust/cargo and sidesteps it. _How to apply:_ when a chosen toolchain is unbuildable here and the fix is a system-level user action, surface it as an issue and prefer an alternative that builds in this environment over waiting on a host fix.
- **Tauri/cargo build operability (loop #12, verified):**
  - **Source `~/.cargo/env` before any cargo/tauri command.** rustup installs to `~/.cargo/bin` but a *non-login* shell (how the loop's Bash runs) doesn't have it on PATH, so a bare `command -v cargo` falsely reports "not installed". Always run `. "$HOME/.cargo/env"` first. _Why:_ avoids re-raising a "Rust missing" issue when Rust is actually present.
  - **`cargo check` is the fast green-light; `tauri build` catches config defects `cargo check` can't.** First `cargo check` compiles all Tauri deps (~1.5 min) then is ~instant cached. But bundle-time validation (e.g. `productName`) only runs at `tauri build`. _How to apply:_ use `cargo check` to confirm the Rust compiles, then a real `tauri build` to validate config + produce the artifact.
  - **macOS bundle `productName` must match `^[^/:*?"<>|]+$`** — no `? : / * " < > |`. Keep illegal branding chars (like the product's `?`) in the **window `title`** / longDescription, not in `productName`. _Why:_ `tauri build` hard-errors otherwise.
  - **DMG bundling fails headless** (`bundle_dmg.sh`/`create-dmg` needs a GUI/Finder session). Default `bundle.targets` to `["app"]` so the loop's build terminates green and produces the runnable `.app`; generate the `.dmg` only in an interactive session via `tauri build --bundles dmg`. _Why:_ keeps the automated build non-hanging and reliable.
  - **Generate icons with `tauri icon <png>` before `tauri build`** (configs reference `icons/*` that aren't committed). A placeholder 1024px source is fine to unblock; trim the `android/`/`ios/` output for macOS-only packaging. _How to apply:_ commit the generated icon set; note the placeholder so a real logo can replace it.
  - **Native build/verify has an irreducible human step.** Compilation + `.app` production are automatable; live tray/global-hotkey/close-to-tray behavior needs a GUI smoke-test. Verify the build green, then hand the user the exact `open …app` + checklist rather than claiming runtime behavior unverified-but-done.

## Collaboration
- **Be proactive with issues**: raise a pending issue for any meaningful product/UX/architecture decision instead of silently picking a default — the user wants their intent captured early, since changes get costlier later (user feedback, [Review 4](../Reviews/processed/Review%204.md)). _How to apply:_ when a default is debatable or hard to reverse, write an issue with options + a recommendation; keep within `unanswered_issue_limit`.
- **Prioritize to user-testable**: each cycle, push implementation to the point where the user can personally run and verify the result, then surface how to test it (user feedback, [Review 4](../Reviews/processed/Review%204.md)). _How to apply:_ favor an end-to-end runnable slice over polishing one layer; after building, launch/verify it and give the user the exact way to try it.

## Privacy implementation rules (from TASK-202606131231)
- **Debug/verification features are off by default and clearly labeled.** Any mode that bypasses privacy (e.g. exact-location "verification mode") must be opt-in, forced off at boot, visibly bannered while active, and must never touch the privacy-safe store/render path. The default send path always routes through `transformSignal` (jitter + bucketing). _Why:_ Review 5 asked for an exact-location verification view; it must not become a way to leak real location by default.
- Jitter must be a **uniform-random point within the geohash cell**, never center-biased (leaks center) and never a fixed offset (subtractable). Draw randomness **independently per signal** so repeated signals from one location scatter across the cell (defeats triangulation).
- The persisted/transmitted record holds **only** `{id, cell, jittered_lat, jittered_lng, t, source}` — never raw GPS, identity, or exact timestamp.
- Display via `visibleCells` enforces **k-anonymity** (default K=3) before a cell is shown.
