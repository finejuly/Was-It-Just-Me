# Native macOS sender — `WIJMCore` (privacy bridge)

The approved native menu-bar sender (TASK-202606131313) reuses the **unchanged,
tested TypeScript privacy core** instead of re-implementing privacy in Swift. This
folder holds **increment A**: the de-risking spine that proves
`Swift → JavaScriptCore → privacy core` parity, fully offline.

Swift writes **zero** privacy logic. It embeds JavaScriptCore (a macOS-bundled
framework, no third-party deps), evaluates a tiny bundled build of the core, and
calls `WIJM.transformSignal(...)` — the exact code path the web app and the
`node:test` suite already verify (jitter + bucketing + timestamp coarsening,
uniform-random point per signal within the geohash cell, six-field record).

## Build & test

1. **Bundle the core** (from the repo root) — regenerate `wijm-core.js` whenever the
   privacy core changes:
   ```sh
   npm run build:core
   ```
   This esbuild-bundles `src/core/bridge.ts` (+ `privacy.ts`, `geohash.ts`) into a
   single classic IIFE script exposing `WIJM.transformSignal` / `WIJM.visibleCells`.
   No ESM, no runtime deps — JavaScriptCore evaluates a plain script.

2. **Build / test the Swift package**:
   ```sh
   cd native/WIJMCore
   swift build
   swift test        # privacy parity: bounded jitter, no raw/identity leak, per-signal scatter, six-field schema
   ```

The bridge contract is **also** covered by the JS suite (`npm test` →
`src/core/bridge.test.ts`), so the privacy guarantee is verified offline with zero
install even before the Swift step.

## Randomness

JavaScriptCore has no Web Crypto, so the core's default RNG/UUID are unavailable in
JSC. The bridge therefore **requires injected** randomness: Swift passes a
`SecRandomCopyBytes`-backed uniform-[0,1) function and a UUID string. This keeps the
entropy source auditable on the Swift side and leaves the core math untouched.

## Status / known blocker (loop #9)

Increment A's **JS half is verified** (`npm run build:core` + `bridge.test.ts`,
57/57). The **Swift half could not be built/tested in this environment** due to a
machine-level toolchain/SDK skew — `swiftc` reports the SDK was built with
`swiftlang-6.2.1.4.7` while the compiler is `swiftlang-6.2.1.4.8`, which breaks
**all** Swift compilation (even a trivial SwiftPM package or a one-file `swiftc`
build), not just this package. See the pending issue raised for the fix
(align Command Line Tools / `xcode-select` to a matching toolchain). Once the
toolchain is realigned, `swift build && swift test` here should pass unchanged.
