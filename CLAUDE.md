# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is **not yet a code repository** — it is a **Loop Engineering** workspace for building a product called **"Was It Just Me?"**. The repo currently contains planning/orchestration documents (Markdown) inside an Obsidian vault, plus the Loop **skills** that drive an autonomous build process. There is no application source, build system, or tests yet; those are meant to be generated by the Loop process described below.

Loop Engineering is an autonomous, iterative LLM development process (reference: https://addyosmani.com/blog/loop-engineering/). The vault is the persistent state that the loop reads from and writes to on each iteration; the skills in `.claude/skills/` are the reusable modules the loop dispatches.

## The product being built ("Was It Just Me?")

Defined in [IDEA.md](IDEA.md). A privacy-preserving neighborhood "signal" map: users send a very low-friction anonymous "I noticed something" signal (hotkey / long-press), visualized as **jittered/bucketed** dots on a map so exact locations cannot be inferred. Key product constraints that should propagate into any implementation:

- **No incident classification** — the only action is "I noticed something". Avoid crime-reporting / surveillance / policing framing.
- **Privacy-first**: locations must be intentionally randomized; raw sender location must never be derivable.
- **Runtime must not depend on Claude or any LLM** — Claude builds the app, it is not a product dependency.
- **Demo mode is a first-class requirement** — simulates nearby signals, false signals, heatmap changes, hotkey triggers, background behavior, and historical replay (the hackathon demo cannot rely on real users).
- Supports live + historical views, heatmap density, and background/low-energy operation.

This is a Claude Build Day hackathon submission — optimize for an impressive live demo.

## The Loop process (from [LOOP.md](LOOP.md))

You act as the **Main Orchestrator**. Each loop iteration:

1. Read `config.md`, `PRD.md`, `Progress.md`, `Preferences.md`, `Issues/*`, `Tasks/*`, `Reviews/`, and recent Run Log entries.
2. Apply `config.md` as the current runtime configuration.
3. Convert anything in `Reviews/` into new Tasks or Issues.
4. **Gate**: if pending issues exceed `unanswered_issue_limit`, do **not** dispatch implementation work — update `Progress.md` and stop.
5. Decide which modules are needed this loop: Discovery, Planning, Implementation, Review, Learning, PRD Maintenance.
6. Dispatch only the useful modules; use **subagents** for independent read/review/planning modules.
7. Modules write findings to module-specific note/task files. **Only the Main Orchestrator updates `Progress.md`, `PRD.md`, and global state.**
8. Only the **Implementation** module may modify product code, run tests, and commit. Other modules must not touch product code unless explicitly dispatched.
9. Create approval/rejection issues in `Issues/pending/` when user input is needed.
10. Keep commits small; update `Run Log/` after meaningful work.

### Runtime config ([vault/Loop/config.md](vault/Loop/config.md))

- `refresh_minutes: 5` — loop cadence.
- `unanswered_issue_limit: 5` — pending-issue ceiling that halts implementation (step 4 gate).

## Loop skills (`.claude/skills/`)

One skill per module/capability the loop dispatches. **Entry point: `loop-orchestrate`** — invoking it runs one loop iteration; it dispatches the rest (read/review/planning modules run as subagents). Full path↔skill ownership and a coverage check live in [vault/Info/Vault-Map.md](vault/Info/Vault-Map.md).

| Skill | Role |
| --- | --- |
| `loop-orchestrate` | Main Orchestrator — drives a loop iteration, owns final `Progress.md`/`PRD.md`/global-state writes |
| `loop-discovery` | Explores PRD/state/Resources → proposes candidate tasks & issues (read-only on code) |
| `loop-plan` | Promotes `candidates` → `ready` with plan + acceptance criteria |
| `loop-implement` | **Only** code-writing module: `ready` → `active` → `done`, runs tests, commits |
| `loop-review` | Independent review of `done` work → findings in `Reviews/` |
| `loop-learn` | Extracts durable lessons → `Preferences.md` |
| `loop-prd` | PRD maintenance / initial generation from IDEA.md |
| `loop-goal` | Regenerates `GOAL.md` from the PRD (run after `loop-prd`) |
| `loop-create-task` | Creates tasks from approved issues + reviews → `Tasks/candidates/` |
| `loop-create-issue` | Raises approval/decision issues → `Issues/pending/` (the human gate) |
| `loop-progress` | Writes `Progress.md` snapshot + appends to `Run Log/` |

## Conventions

- This is the active branch's clean state on `main`; product code does not exist yet — don't assume build/lint/test commands until the Implementation module scaffolds the app and this file is updated with them.
- Respect the directory state machines: Issues flow pending→approved/rejected; Tasks flow candidates→ready→active→done. Move files between these folders rather than inventing parallel tracking.
- Treat `vault/` as Obsidian content — `[[wikilinks]]` and Markdown are the expected note format.
